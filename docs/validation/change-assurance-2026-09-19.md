# 변경 입력부터 Calendar 재확인까지 — 로컬 검증 기록

2026-09-19 구현·로컬 검증을 완료했다. 공개 사이트 배포와 실제 Google 재확인은 아직 수행하지 않았다.

## 사용자가 달라지는 점

1. 복사한 안내문을 원문 화면에서 미리 보고 가져온다. 작성 중인 초안이 있으면 바꿀지 확인한다. 가져오기만으로 저장하거나 AI를 호출하지 않는다.
2. 일정 조정 화면에서 영향 계산, 이어짐에 적용, Calendar에 반영, 이후 상태 확인을 구분한다.
3. 승인 후 반영했던 Calendar 일정을 다시 읽어 제목·시각·메모·식별 정보·버전이 달라졌는지 확인한다. 삭제·조회 실패도 따로 표시한다.
4. 사용자가 켜면 최대 24시간 동안 15분 간격으로 읽기 전용 확인을 예약한다. 외부 변경·연결 해제·기준 변경·연속 실패를 만나면 중지하고 판단을 사용자에게 돌려준다. 처리량에 따라 예약보다 늦어질 수 있다.

외부 상태가 달라졌다고 과거 실행 이력을 지우거나 자동으로 일정을 덮어쓰지 않는다. 새 유료 모델 호출, 메일 발송, 브라우저 자동 조작을 이 재확인에 섞지 않았다.

## 발견하고 고친 문제

- 외부 조회가 끝난 뒤 결과 저장 직전에 승인 기준이나 인증 버전이 바뀌는 경합: 최종 SQL 갱신에서도 같은 기준인지 확인한다.
- provider 초기화 실패가 반복 실패 횟수를 다시 1로 만드는 문제: 같은 실패 예산으로 누적하고 3회에서 멈춘다.
- 취소된 Google 이벤트에 일부 필드가 남아 정상처럼 읽히는 문제: sparse/full 취소 응답과410을 결측으로, tentative 응답을 충돌로 처리한다.
- 진행 중 재확인을 중지했는데 이전 일치 문구가 남는 문제: 미완료 관찰을 비우고 기존 실행 이력만 보존한다.
- 수동 조작 전에 시작한 GET이 늦게 돌아와 화면을 되돌리는 문제: 수동 요청 시작 시 조회 세대를 바꾸고 이전 응답을 버린다. 브라우저에서 먼저 실패를 재현한 뒤 수정했다.

브라우저 최초 2개 실패는 새 테스트가 textarea의 내용까지 포함한 label을 정확히 찾으려던 문제였다. 접근성 이름으로 textbox를 찾도록 고쳤으며 초안 보호·저장 금지 기대값은 유지했다.

## 다시 확인할 범위

로컬 테스트는 실제 Google 사용자 계정이나 장시간 운영 결과를 증명하지 않는다. 외부 변경 후 재조회, 반복 확인 중지, 실제 공급자 장애와 Google quota는 배포 후 별도 승인된 계정에서 확인해야 한다. 여러 이벤트를 읽는 과정은 원자적 snapshot이 아니다. 처리량 상한과 예약 지연, 운영 중지, migration-first 배포 순서는 [운영 문서](../operations/calendar-verification-2026-09-19.md)에 있다.

직접 열어볼 로컬 미리보기: http://127.0.0.1:5175/recovery . 이 keyless 환경에서는 합성 일정 저장·승인을 확인할 수 있고 실제 Google 연결이나 AI 호출은 하지 않는다. Calendar 관찰 UI 이미지는 fake-provider 브라우저 시험 자산이며 제출용 실서비스 캡처가 아니다.

범용 브라우저 실행, 전체 메일함 수집, 자동 외부 수정은 별도 단계로 남겨 두었다. 이번 완료는 [9월19일 설계 범위](../design/change-assurance-2026-09-19.md)를 대상으로 한다.
