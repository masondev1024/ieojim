# 첫 상업 타깃과 준비 업무 구현 결정

날짜: 2026-09-14. 사용자 요청: 기업 비서·병원·학교 후보 중 타깃을 확정하고 전략 초안대로 구현 시작.

> 후속 사용자 요청으로 제품 전체의 제출 방향은 [범용 제품 방향](submission-positioning-2026-09-14.md)으로 수정했다. 아래 기업 타깃은 한 용례와 상용화 가설의 기록이며, 구현 완료 범위는 유지한다.

## 당시 선택

첫 사용자는 **소규모 기업에서 외부 미팅·행사의 변경 요청과 준비 업무를 관리하는 비서·경영지원 담당자 한 명**이다. 구매자는 대표 또는 운영 책임자라는 가설이다. 대상은 특정 기업 규모 통계로 검증된 세그먼트가 아니며, 아직 인터뷰·반복 사용·결제 증거가 없다.

사용할 이유는 새 요청을 일정·자료 마감·준비 목록으로 만들고, 정정이 오면 관련 작업을 수정하면서 고정 약속·완료 기록·직접 입력한 준비 설정을 보존하는 것이다. 담당자 자신의 업무를 지원한다. 임원 계정에 위임 로그인하거나 여러 참석자를 대신해 초대·예약을 확정하는 제품으로 소개하지 않는다.

## 후보 비교와 반론

| 후보 | 첫 업무 | 지금 선택의 판단 |
|---|---|---|
| 기업 비서·경영지원 | 미팅 변경에 따른 준비 목록·자료 마감·안내 초안 관리 | 현재 원문/변경/사용자 결정 보존 모델과 잘 맞는다. 단일 소유자로 한정해 먼저 구현한다. |
| 병원 행정 | 내부 회의·행사 준비 또는 환자 예약 조정 | 내부 업무는 향후 같은 흐름을 쓸 수 있다. 환자 예약을 첫 목표로 삼으면 환자 데이터와 진료/예약 시스템·오예약 대응이 별도 제품 범위가 되므로 보류한다. |
| 학교 행정 | 교직원 회의·행사 준비 또는 학생/학부모 일정 관리 | 교직원 내부 업무는 후속 후보. 학생 정보·학부모 연락·조직 승인이 필요한 흐름은 현재 단일 owner 모델로 제공한다고 주장하지 않는다. |

강한 반론: 비서가 원하는 기능은 남의 캘린더 조정과 초대까지일 수 있다. 준비 관리만으로 구매 이유가 충분한지는 미검증이다. Reclaim은 이미 비서를 위한 일정 관리와 위임 접근 기능을 설명한다. 따라서 단순 일정 조율을 독보적인 기능으로 내세우지 않는다. [Reclaim 위임 접근 안내](https://updates.reclaim.ai/announcements/delegated-access-to-your-reclaim-account)

향후 Calendar 첫 실행은 앱이 만든 보조 캘린더의 자체 이벤트로 제한하는 기존 초안을 유지한다. Google의 `calendar.app.created`는 이 범위를 지원한다. 별도 관리자 승인·위임 계정까지 지금 구현할 근거는 없다. [Google Calendar 권한](https://developers.google.com/workspace/calendar/api/auth)

이 선택은 독립 critic의 조건부 OKAY를 받았다. 조건은 기업 단일 담당자 업무에 한정하고 병원 예약·학생 기록·조직 위임·메일 송신을 포함하지 않는 것이다. 이는 설계 검토 결과이며 시장성 검증이 아니다.

## 이번 구현 범위

1. `/assistants`에서 기업 미팅 실제 원문 입력과 명시적인 합성 예시로 진입한다. 기존 여행 진입은 회귀 기능으로 보존한다.
2. 새 `coordination` 예시는 미팅 시간/장소/자료 마감 변경, 고정 보고 시간 충돌, 완료된 인쇄본 항목 삭제, 직접 쓴 안내 보존을 같은 core로 처리한다.
3. 모든 작업 공간의 checklist에 사용자 지정 마감 날짜와 예상 분을 저장한다. 모델의 추정치라고 표현하지 않는다. 신규 요청부터 준비 내용을 관리할 수 있어 fixture에만 종속되지 않는다.
4. preparation은 사용자 소유의 선택적 version 1 메타데이터다. 새 모델 출력에는 허용하지 않는다. 두 입력이 비면 제거하며, 설정이 있는 항목 삭제에는 보호가 필요하다.
5. 원문 변경으로 사용자 날짜를 조용히 움직이지 않는다. 관련 변경은 재검토 상태로 보여 준다. 준비 정보만 수정해 본문 검토 경고를 지우지 않는다. 사용자가 내용을 확인한 뒤 명시적으로 `acknowledgeReview: true`를 보내면 준비 항목의 경고만 해제한다. 완료 여부·본문·잠금·준비값은 유지하고 새 revision을 남긴다.
6. 기존 owner·CAS·idempotency·source revision·복원을 재사용한다. 저장 성공은 서버가 확인한 뒤 표시한다.

## 데이터 계약과 배포 주의

선택적 metadata이므로 기존 저장 자료는 새 코드에서 그대로 읽는다. 현재 export의 snapshot과 직전 이력에도 해당 필드를 포함한다. 새로운 필드를 모르는 구버전 strict reader가 읽을 수 있다는 보장은 없다. 공개 배포 시 새 client/server를 함께 배포하고, 새 metadata를 기록한 뒤 구버전 binary만 롤백하지 않는다. 롤백 후보는 해당 필드를 읽고 보존할 수 있어야 하며, metadata를 삭제하는 복구는 승인 없이 수행하지 않는다.

비활동 7일 보존, 기존 원문/항목/사용량 상한은 이번에 바꾸지 않는다. 장기 유료 보존·계정 삭제·외부 캘린더 잔존 이벤트 정책은 실제 실행 공개 전에 정해야 한다.

## 검증과 다음 단계

초기/정정 fixture, 가능한 충돌 선택 조합, 메타데이터 보존/삭제 보호/날짜 검증, API 소유권·중복·오래된 revision·export·restore, 실제 브라우저 신규 진입/저장/재접속을 확인한다. 기존 검사 기준은 고정하며 신규 회귀를 추가한다. `npm run verify`와 root 소유 격리 브라우저 검사 후 독립 리뷰를 받는다.
