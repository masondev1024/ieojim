# 출발 전날 변경 — 첫 화면 개편

사용자가 지적한 문제는 계산의 난도가 아니라 제품을 써야 할 이유가 보이지 않는다는 점이었다. 인원으로 총액을 나누는 장면은 보조 설명으로 내리고, 여러 변경이 기존 결정과 충돌하는 순간을 첫 체험으로 올렸다.

## 보여 주는 상황

출발 전날 하나의 정정 안내가 온다. 인원은 4명에서 3명으로 줄고, 도착은 10시에서 16시로 밀린다. 저녁 약속을 19시에서 20시로 바꾸고, 이미 완료한 종이 확인서 출력 항목을 삭제하라는 요청도 들어 있다. 사용자가 직접 쓴 공유 메모에는 종이 확인서를 챙기겠다는 문장이 남아 있다.

| 상황 | 제품 동작 | 드러나는 엔지니어링 |
| --- | --- | --- |
| 인원·도착 변경 | 전후 값과 실제 원문 인용 표시 | 구조화된 사실, 출처 연결 |
| 고정비 90만 원 유지 | 1인 22.5만 원 → 30만 원 계산 | 사실과 파생 계산 분리 |
| 잠근 저녁 변경 | 현재 결정 유지 / 새 원문 적용을 선택 | 사용자 결정 보호와 명시적 권한 |
| 완료한 항목 삭제 | 별도의 삭제 선택을 요구 | 보호된 상태의 삭제 차단 |
| 직접 쓴 문장과 새 안내 불일치 | 내용을 보존하고 재검토 표시 | 사용자 편집과 최신성 분리 |
| 선택 결과 저장과 되돌리기 | 저장 후 재조회, 이전 내용을 새 리비전으로 복원 | 원자적 적용, 중복 방지, 내용과 원문 이력 분리 |

## 체험의 경계

첫 화면은 **합성 예시·브라우저 미리보기**다. 사용자가 버튼을 누르면 실제 서비스의 `buildChangeSet`/`resolveChangeSet`을 불러와 결과를 만든다. 네 선택 조합은 같은 초기 snapshot으로 각각 계산된다. API·모델을 호출하거나 저장하지 않는다. 사용자가 선택을 바꾸면 이전 결과는 사라진다.

`/app?example=departure`에서 **출발 전날 복합 체험 시작**을 눌러야 같은 예시가 실제 작업 공간으로 생성된다. 기존 D1/API 경로에서 두 선택을 반영하고 새로고침·복원을 확인한다. 복원은 원문 카탈로그나 비용 장부를 되돌리지 않는다. 이전 단순 여행/과제 샘플도 유지한다.

이는 복잡한 여행을 자동 최적화하거나 예약을 대신하는 기능이 아니다. 외부 채팅·항공·숙박 연동을 새로 추가하지 않았다. 합성 체험의 성공은 새 입력에 대한 모델 정확도나 경쟁 제품 대비 우위를 측정한 결과가 아니다. 실제 모델 평가와 사용자 검증 기록은 별도로 유지한다.

## 심사 시연 순서

1. 첫 화면에서 **출발 전 변경 검토하기**를 누른다. 두 필수 선택을 하지 않으면 결과 비교가 비활성화됨을 보여 준다.
2. 각 항목의 **원문 근거 보기**를 펼친다. 저녁은 유지하고 종이 확인서는 삭제하는 조합으로 결과를 비교한다.
3. 원문 변경을 따르더라도 직접 쓴 공유 문장은 덮어쓰지 않고 재검토 대상으로 남는 점을 설명한다.
4. 같은 예시를 실제 작업 공간에서 생성하고 **출발 전날 정정 안내 불러오기**를 누른다. **변경 검토**에서 두 항목을 선택해 반영한다.
5. 새로고침 후 값이 유지되는지 확인하고 **변경 이력 → 1번 내용 복원**을 실행한다. 내용은 복원되지만 정정 안내 원문은 남는 점을 보여 준다.

이 체험이 어필하는 가치는 “답을 한 번 생성”하는 능력보다 **새 안내가 와도 이미 해 둔 작업을 안전하게 이어 가는 능력**이다. 현재 배포 버전과 정확한 검증 수치는 `PLANS.md`의 최신 체크포인트 및 `.omx/verification-departure-story.json`을 따른다.
