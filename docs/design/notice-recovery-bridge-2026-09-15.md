# 안내문에서 일정 복구로 연결

기존 Gemini 실행이 만든 작업 공간의 승인된 원문·사실·항목을 가져온다. 별도 모델 호출 없이 사용자가 실행에 필요한 조건을 확인한다. 기존 범용 fact는 시간 구간이나 빈 시간을 보장하지 않으므로 모델 값을 실행 권한으로 승격하지 않는다.

## 범위와 데이터 계약

- 원래 작업 공간은 보존하고 별도의 복구 작업 공간을 만든다. 출처 작업 공간의 소유자·내용 버전·원문 버전·선택한 원문 ID/hash·항목 매핑을 `recovery_origins`에 보관한다. 생성 트랜잭션과 읽기·승인·외부 작업 등록 및 실행 전 검증에서 기준을 확인한다.
- 원문과 사용자가 확인한 조건 문서는 서로 다른 immutable source로 저장한다. 실제 안내의 인용은 실제 원문을 가리키고, 시간·관계 확인의 권한은 조건 문서의 `user_confirmed` 근거를 사용한다. 이 단계에는 가짜 fixture/live run을 생성하지 않는다.
- 최초 경로는 일정 하나, 준비 하나, 일정 직전 이동을 지원한다. 가용 시간과 원래 작업 공간의 다른 모든 일정 구간을 사용자가 확인한다. 기존 일정은 기본 보호하며 명시적으로 고른 최대 한 항목만 정해진 시간 안에서 이동한다. 잠금·완료·직접 편집·확인 필요 상태의 항목은 이동 대상으로 사용하지 않는다.
- Asia/Seoul, 최대 48시간·30개 일정·이동 가능한 다른 업무 1개라는 기존 계산 범위를 유지한다. 상대 날짜나 빠진 연도는 추정하지 않는다. 화면은 full date_time fact만 후보로 보여준다.
- 준비 항목은 기존 체크리스트에서 선택하거나 새 준비 작업임을 명시해 만든다. 기존 준비 설정이 있으면 그대로 따라야 하며 잠금·완료·직접 편집 상태를 조용히 덮어쓰지 않는다.
- 실제 복구 화면은 확인한 조건을 읽기 전용으로 제시한다. 조건을 변경하려면 출처 작업 공간에서 새 복구안을 만든다. 기존 합성 화면의 반례 편집 경로와 분리한다.
- 복구안 승인과 Google Calendar 반영 승인은 별개다. 기존 전용 Calendar, idempotent outbox, etag·재조회 검증을 사용한다. 원래 작업 공간이나 기존 Google 일정에 자동으로 덮어쓰지 않는다.

## 구현 경계

Core는 strict request schema와 순수한 seed builder를 제공한다. Server는 원문/사용자 상태를 직접 읽고 D1 생성·기준 검증·중복 요청을 담당한다. Client는 단계별 입력과 실제 원문 근거를 표시하고 확인 후 서버 계산 결과로 이동한다. 루트만 테스트·빌드·브라우저·배포 프로세스를 실행한다.

이번 단계는 별도 AI recovery extraction schema, Calendar 전체 일정 import, 다른 사람의 빈 시간 추정, 반복 일정, 다중 시간대, 자동 이메일 발송을 추가하지 않는다. 이미 승인한 AI 정리 결과를 실제 실행 가능한 사용자 확인 조건으로 이어 주는 첫 경로다.
